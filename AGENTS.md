# Execution environment

- On Windows run project commands through `dev.cmd`, with `login: false` for exec tools. This pins Node and normalizes the inherited environment, without loading PowerShell profiles.
- At the start of a new session run `./dev.cmd doctor`. Do not reinstall Node or rewrite user PATH to repair a stale shell.
- If external reads are denied, run `./dev.cmd node tools/check-sandbox.mjs` once. The persistent read policy and installers are in `tools/`; do not restart broad host investigation or repeatedly ask to read VS Code internals. Distinguish saved configuration from an active grant.
- Use `./dev.cmd node ...`, `./dev.cmd npm ...`, `./dev.cmd mise ...`, `./dev.cmd git ...`, `./dev.cmd rg ...`, or `./dev.cmd ps '...'`. From subdirectories use the absolute path to the workspace's `dev.cmd`.
- Do not use inline Node (`node -e`, `--eval`, `-p`) or PowerShell scripts for routine agent inspection. Use `dev.cmd rg -n` with explicit paths and separate `-e` patterns. Use named, reviewable scripts for diagnostics that need code, and existing npm scripts for tests. Never request a persistent approval prefix for Node, an inline interpreter, or the entire `dev.cmd` launcher. Saved read grants do not guarantee that a command avoids host approval.

- The machine tool locations are recorded in `tools/toolchain.json`; the project Node version is in `mise.toml`. Keep these and the bootstrap path in `dev.cmd` consistent when intentionally changing versions.
- Child-process environments have one canonical spelling per key. Runtime caches and temporary files belong in `.cache/`, not in the user installation or drive root.
- Do not dump credentials, complete environment variables, authentication files, or unrelated user settings when diagnosing tools.
- A managed host can override Codex permission settings. Do not claim a filesystem read grant is active until a sandboxed read proves it. Never turn off the sandbox to repair tool discovery.
