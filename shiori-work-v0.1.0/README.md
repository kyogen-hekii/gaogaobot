# しおり Work v0.2.0

**相談し、範囲を決めて仕事を任せ、結果と必要な判断を受け取るローカルBotです。**

Muse系の会話中心UIを出発点に、仕事の目的・受け入れ条件・承認・実行・成果を分離しました。Grok Botのような「相談する → 任せる → 必要な判断で戻ってくる」体験を参考にしていますが、Meta／xAI／Cursorの製品・契約・APIには依存しません。foyerのコード、beads、pstack本体は同梱していません。

> **実装済みのローカル試作であり、社内共有サービスとして完成した製品ではありません。**
> 初期設定はデモです。実AI・外部サービス・コード変更を行わず、操作の一往復を試せます。
> Claude CodeはWindowsの既存ログインで、ツールを無効にした実応答・構造化JSON・同一セッション継続を検証しました。実資料の送信・実ファイル編集とCopilotの実アカウント結合は未検証です。

## 開発中だけCodex execを使う

workspaceルートの [start-bot-codex.cmd](../start-bot-codex.cmd) を起動し、[Codex開発画面](http://127.0.0.1:4319) を開きます。会話の判断と作業委託には、プロジェクト専用のCodex CLI 0.166.0と既存のログインを使用します。追加のAPIキー入力は不要です。初回の依存導入は、このアプリのディレクトリで `..\dev.cmd npm ci --cache .cache/npm` を実行します。このworkspaceでは導入済みです。

通常版の設定・履歴は維持し、開発版の会話・仕事・実行記録は `.cache/codex-dev/` に保存します。開発版を止めて通常の [start-bot.cmd](../start-bot.cmd) を起動すれば、元の接続を使えます。

```powershell
# このアプリのディレクトリから
..\dev.cmd npm run dev:codex       # 起動: http://127.0.0.1:4319
..\dev.cmd npm run stop:codex      # 実行中の仕事がない場合に停止
..\dev.cmd npm run doctor:codex    # 実行ファイル・CLI仕様・ログイン可否
..\dev.cmd npm run smoke:codex     # 合成テキストで構造化応答・会話継続を検証
..\dev.cmd npm run smoke:codex:workspace # 空の試験用仕事場に合成ファイルを作る
```

- 文章処理・調査は `codex-read` を選び、「この仕事を任せる」で範囲・回数・期限を指定します。`codex-edit` のアダプターも実装済みですが、このWindows環境ではsandbox内のファイル作成試験が失敗したため、起動設定では無効です。`smoke:codex:workspace` の成功後に [開発用設定](scripts/codex-config.mjs) で有効化してください。
- `exec --json` と厳密なセッションIDで継続し、別の会話の「最後のセッション」を流用しません。管理応答にはJSON Schemaを指定します。
- 管理側は `:read-only`・シェル無効、調査は `:read-only`、変更用アダプターは `:workspace` の権限プロファイルを使います。Codex内の追加承認を待たせず、必要な権限がなければ結果に理由を返します。Botの実行上限・停止・人間の受け入れ確認は引き続き有効です。
- 個人のCodex設定を読み込まない専用実行です。既存認証は利用しますが、追加のMCP・plugins・apps・web検索は使いません。Windowsでは子プロセスにnative sandboxを明示します。ホストの権限設定は変更しません。
- 実行ファイルは [package.json](package.json) と [package-lock.json](package-lock.json) に固定したプロジェクト依存を使用します。古いエディター同梱CLIやPATH上のCLIへの自動フォールバックはしません。依存がなければ導入手順を表示して停止します。別の実行ファイル・モデルを明示する場合のみ `SHIORI_CODEX_COMMAND`（絶対パス）・`SHIORI_CODEX_MODEL` を使えます。
- ローカルCLI経由でも推論はCodexの接続先サービスで行われ、利用枠は既存のCodex契約に従います。会話・作業指示と、作業中に必要となったファイル内容がモデルへ渡ります。

実行方式はOpenAIの [非対話モード](https://learn.chatgpt.com/docs/non-interactive-mode) に準拠しています。WindowsではCLIを起動する親プロセスにも認証・実行ファイルへのアクセスが必要で、ホスト側の承認を必ず不要にする機能ではありません。

## v0.2で追加したこと

### 接続先とモデルを選ぶ

設定の「アウターの判断エンジン」で **Claude Code** / **ChatGPT（Codex経由）** を切り替え、その下の「相談・判断に使うモデル」でモデルを選びます。画面上部にも現在の接続先とモデル指定を表示します。

- 「自動」はモデルIDを指定せず、ClaudeはCLI側の設定、Codexは標準設定を使用します。明示選択はCLIの `--model` に渡します。
- Codexの候補は起動時に `codex debug models` で取得します。同梱一覧への固定はしませんが、CLIの一覧自体が新モデルを含まない場合もあります。「モデルIDを直接指定…」から追加できます。取得失敗は画面に表示します。
- Claudeの `opus` / `sonnet` はCLIが最新系列へ解決する別名です。`ANTHROPIC_DEFAULT_OPUS_MODEL` などで固定されている場合はその指定が優先されます。バージョン固定にはモデルIDを直接指定してください。[Claude公式のモデル設定](https://code.claude.com/docs/en/model-config)。利用できるモデルは接続先・ログイン・CLIの対応に従います。
- 選択は接続先ごとにSQLiteに保存し、次に依頼する相談・判断から反映します。実行中・待機中の依頼は受付時のモデルを維持します。
- 接続先・モデルが変わると、それぞれに対応するCLIセッションを使います。アプリに保存した会話・目的・判断を文脈に添えます。別モデルにCLI内部の全履歴を移植する処理ではありません。
- インナーの実作業モデルは各仕事場の `model` 設定で独立して指定します。相談モデルの変更で、承認済みの実作業モデルは変わりません。
- ChatGPT接続は既存Codexログインを利用します。ChatGPT Webの会話を取り込むものではありません。[OpenAI公式の認証説明](https://learn.chatgpt.com/docs/auth?surface=cli)、[CLIのモデル指定](https://learn.chatgpt.com/docs/cli/reference)。

通常起動の設定にもChatGPTを追加する場合は、このアプリのディレクトリで `..\dev.cmd npm run setup:codex` を一度実行し、サーバーを再起動します。既存の選択や認証情報は変更しません。4319の開発用起動では、登録済みClaude接続とCodexを同じ画面で選べます。

- 「この仕事を任せる」で、仕事の版・実行先・読取り／変更・最大回数・期限を一度指定します。
- 結果を受けて受け入れ条件を評価し、不足があれば同じ委任の範囲内で追加実行します。毎回の承認は不要です。
- 上限、期限切れ、条件・接続設定の変更、権限不足、実行失敗、利用者の停止で自動続行を止めます。
- 条件ごとの評価と根拠、消費回数、停止理由を仕事の詳細に表示します。AIの「確認済み」と、人間による仕事の完了は別です。
- 従来の「作業を依頼」から1回だけ承認して実行する操作も利用できます。

## すぐ動かす

Node.js **24以降**を使用します。このworkspaceでは既存のmise版 **24.19.0** に固定済みです。Codex接続用の開発依存は `..\dev.cmd npm ci --cache .cache/npm` で導入します。サーバー本体はNode標準ライブラリを使用します。

Windowsではworkspaceルートの [start-bot.cmd](../start-bot.cmd) で起動できます。開発コマンドは [dev.cmd](../dev.cmd) を使用します。

```powershell
# このアプリのディレクトリから
..\dev.cmd npm start
..\dev.cmd npm stop
..\dev.cmd npm test
..\dev.cmd npm run doctor -- --probe
```

他のOSでは通常のNode 24環境から次のコマンドで起動します。

```sh
npm start
```

ブラウザで `http://127.0.0.1:4317` を開きます。終了はターミナルでCtrl+Cです。ローカル設定がなければデモモードです。このworkspaceではClaude Codeを接続済みです。データを残さないデモは `..\dev.cmd npm run demo` → `http://127.0.0.1:4318` で利用できます。

```sh
npm run doctor  # Node・設定・CLIの存在を確認。モデルは実行しません
npm test        # サーバー・管理ロジック・模擬CLIの自動試験
```

Windowsネイティブでサーバー・SQLite・模擬CLI・Claudeの会話接続を検証しています。CLIが起動した子孫プロセスすべての終了を保証するOSプロセス管理は未実装です。

`preview.html`は、ブラウザで直接開ける別の画面体験版です。実サーバー版と同じUIを使いますが、バックエンドはブラウザ内の模擬動作で、再読み込みするとリセットされます。CLI・SQLite・常駐監視は使いません。画面上部にもその区別を表示します。

## 最初に試す一往復

1. チャットで「来週の設計レビューに向けて未決事項を整理してください。今回は調査までで、まだ改修はしません。」と依頼します。
2. 作成された仕事を開き、目的・受け入れ条件・制約を確認します。必要なら「条件を編集」で変更します。
3. 「この仕事を任せる」から仕事場・範囲・最大回数・期限を指定して開始します。
4. アクティビティと成果物を確認します。デモの出力には、実コード変更・実テストをしていないことを明記しています。
5. 不足があればBotが範囲内で追加依頼します。手動の追加指示も同じ仕事の会話に残せます。停止ボタンは実行と残りの委任を止めます。
6. 成果物を確認し、受け入れ条件をすべてチェックして完了にします。CLIの正常終了だけでは仕事を完了にしません。

「定期確認」では、対象と確認間隔を登録できます。有効な委任がない仕事は整理・提案までで止まります。有効な委任がある場合も、その残り回数と期限に従います。サーバー停止中は動きません。

## 実AIをつなぐ

Windowsで既存のClaude Codeログインを使う場合は `..\dev.cmd npm run setup:claude` で接続設定を保存できます。再インストールやPATH変更はしません。`..\dev.cmd npm run smoke:claude` は固定の疎通メッセージ2回だけを送って会話と継続を検証し、ローカル資料は送りません。CLIの認証情報は読み出し・コピーしません。

このセットアップは、読取り用と編集用の仕事場をこのアプリのディレクトリに登録します。編集用はClaudeの `--restricted` と明示したファイルツールだけを使い、シェル起動は含みません。別リポジトリを対象にする場合は、その仕事場の `cwd` と許可ツールをローカル設定で変更します。

### 1. 接続する場所を決める

v0.2では、**アプリサーバーとCLIは同一ホスト**で動きます。仕事用PC・WSL・承認済みVMなどに置きます。別ホストRunnerへのSSH／HTTP転送は未実装です。

ブラウザがCLIを直接操作するのではなく、サーバーが管理者の登録したディレクトリでCLIを起動します。ログインもそのサーバーの実行ユーザーで行ってください。CLIごとのログイン手順・会社の利用規程・無人実行の可否を確認してください。

### 2. 設定を作る

```sh
cp config.example.json config.local.json
```

`config.local.json`はGit管理対象外です。認証トークンは記述しないでください。

- `providers`：**アウター自身**の推論を担当するCLIです。管理用の作業ディレクトリを使います。
- `runners`：**インナー**の仕事場です。対象リポジトリのディレクトリを指定します。
- それぞれ必要なプロファイルだけ`enabled: true`にします。
- 変更後はサーバーを再起動します。
- 画面の「設定」から有効なOuter Providerを選びます。初回作成済みDBでは選択済みの値が残るため、設定ファイルの`outerProvider`を書き換えるだけでは既存選択は変わりません。

Claudeを使う例：`providers`の`claude.enabled`を`true`にします。インナーも使う場合は`claude-dev.enabled`を`true`にし、`cwd`を実在する対象リポジトリの絶対パスに変更します。最初は`allowWrite: false`のままで試してください。

Copilotを使う場合も同様です。`command`は実行ファイルの名前か絶対パスであり、オプション付きのシェル文字列ではありません。

```sh
npm run doctor -- --probe
```

`--probe`は有効なCLIの`--help`を呼び、主要なオプションの存在を調べます。認証、課金、JSONLの実応答、セッション継続の成功を保証する検査ではありません。必要なオプションがないCLIでは、バージョンを確認してから利用してください。

### 3. 読取りだけで結合を確認する

対象に機密情報を含まない検証用リポジトリを用意します。実行先を選び、「READMEの内容と未確認事項を整理」と依頼して承認します。結果が返ること、アクティビティに実行が残ること、同じ仕事への追加依頼でセッションIDが継続することを確認します。

認証失敗や未対応オプションの場合はエラーを表示して停止します。別モデルやAPI課金に自動で切り替えません。ただし、**CLI自体の認証・プロバイダー設定・環境変数による課金経路は別**です。このアプリだけでサブスク利用を保証するものではありません。

### 4. 変更作業とpstackは、仕事場側で整える

pstack本体は同梱していません。利用するCLI／ハーネス向けに、対象リポジトリで事前に導入・検証してください。Claude向け設定がそのままCopilotで同等に動くとは限りません。

変更を許可するには、ローカル設定で`allowWrite: true`にし、必要な`allowedTools`だけを追加します。Claudeなら`Read`・`Glob`・`Grep`・`Edit`・`Write`など、Copilotなら実際のCLIが受け付ける許可パターンを使います。テスト起動のためのシェル許可は範囲を限定してください。

**この設定はOSサンドボックスではありません。** 許可したシェル、既存のCLI設定、Hooks、MCPは別のリスクになります。信頼できないリポジトリで動かさず、レビュー済みの専用OSユーザー・VM・コンテナ等で検証してください。権限バイパスや`--allow-all`はアプリから付与しません。

## セッションの扱い

仕事ID、論理セッションID、ベンダーのセッションID、1回の実行IDを別々に保存します。

- 同じ仕事・同じ実行先・同じ設定では、明示的なベンダーセッションIDを指定して継続します。
- 全仕事を一つのセッションへ詰め込みません。「直前のセッション」を曖昧に再開する方法も使いません。
- `cwd`・モデル・許可設定などが変われば別セッションになります。
- 仕事の詳細から次回のセッションを切り替えられます。目的・条件・判断・一部の成果物を引き継ぎますが、CLI内部の全会話履歴の移植ではありません。
- セッションの履歴ファイルとログイン情報はCLIが管理します。しおりのDBだけを別マシンに移しても、そのまま再開できる保証はありません。

## 保存・停止・復旧

既定の保存先は`.data/shiori.sqlite`です。設定、会話、仕事、承認、結果、イベントを保存します。データは暗号化していません。作業中の端末、CLIの履歴、出力先も含めて社内ルールで保護してください。

バックアップはサーバーを正常停止してから`.data/`をコピーしてください。稼働中のSQLite本体ファイルだけのコピーでは不整合の危険があります。画面の「JSONを書き出す」は閲覧・記録用で、完全な復元用バックアップ／インポート機能ではありません。

ブラウザを閉じてもサーバーが動いていれば処理は継続します。サーバーが異常停止した実行は、再起動時に`interrupted`となります。アクティビティから、実ホストのプロセス終了と途中成果を確認してロックを解除してください。**勝手な再実行はしません。** 再起動後も独立したCLIプロセスが残る可能性があります。

`dailyRuns`はOuter・Inner合計の起動回数上限で、UTC日付でリセットします。料金やトークンの正確な上限ではありません。上限で待機した実行は翌日以降に再開対象となりますが、承認期限切れの場合は新しい承認が必要です。

## 意図的に含めていないもの

SSO／マルチユーザーRBAC、SlackやTeamsの実接続、汎用ブラウザ操作、メール・カレンダー検索、PDFの自動読取り、遠隔Runner、強固なOS隔離、正式な監査保管、課金額の厳密な管理は含めていません。全機能を自律稼働させる完成品ではなく、まず一人の業務で管理の一往復を検証するための基盤です。
