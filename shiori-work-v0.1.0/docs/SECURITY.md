# 安全性・信頼境界・業務導入前の条件

## この版の位置づけ

本版は、**信頼したOSユーザーがlocalhostで使う単一ユーザー試作**です。仕事用に必要な管理境界を検証しますが、社内共用のセキュリティ審査を通過した製品ではありません。

## 実装した制御

- 待受けは127.0.0.1限定。Hostをlocalhost／127.0.0.1に限定します。
- 別Originおよびcross-siteを拒否し、JSON書き込みにはCSRFヘッダーを要求します。
- CSPを設定し、資料・モデルの出力をHTMLとして実行しません。
- 実行先はローカル設定の登録済みprofileのみ。任意コマンドやcwdをブラウザから追加できません。
- 子プロセスはshell:false、依頼文は標準入力で渡します。
- Outerの許可操作から承認・完了・任意実行を除外しています。
- 実行依頼は人間の承認を必要とし、要求revisionと設定fingerprint、依頼digest、30分の期限に結びます。
- 同一セッションとInnerの同一workspaceを同時実行しません。
- 操作ID、イベントID、承認IDの重複で同じ処理を二重に発注しないようにします。
- 出力量・タイムアウト・起動回数・キュー長を制限します。
- CLIがエラーを返した際に、権限バイパス、別モデル、別API課金へ自動変更しません。
- しおり固有の環境変数SHIORI_*はCLI子プロセスへ渡しません。
- 再起動で実行の成否が不明ならinterruptedとして、照合までロックを維持します。

これらは安全性を高める制御ですが、完全な隔離・データ流出防止・利用者認証を意味しません。

## 重要な限界

### 1. localhostは認証の代わりではない

UIはGET /api/stateからCSRF値を取得します。CSRFはブラウザの別サイトからの操作を抑えるためのもので、ホスト上の別プロセスや同じOSユーザーに対するアクセス制御ではありません。TLS・ログイン・SSO・RBACは未実装です。共有ネットワークへ直接公開しないでください。

### 2. 承認は依頼単位であり、CLI内の全操作を監督しない

UIの承認は、表示した作業依頼を起動してよいかを管理します。CLIのツール呼び出し一つひとつを同じUIへ中継するpermission callbackは実装していません。CLIは事前の許可範囲で動き、許可できない操作は拒否または停止します。

プロンプトに「pushしない」「外部送信しない」と記載しても、許可したシェルからの通信をOSレベルで止めることはできません。sandbox、ネットワーク出口、サービスアカウント権限、秘密のマウント範囲が別途必要です。

### 3. リポジトリとハーネス設定は信頼対象

Innerはレビュー済みの仕事場を起動するため、CLIの規則・Hooks・Skills・MCP等が動作する可能性があります。特にClaudeの通常-pは、対話的なフォルダ信頼の確認なしにHooksやMCP設定を読むことが公式資料で説明されています。読取りモードで主要ツールを制限していても、起動フックまでOS隔離しているわけではありません。

Outerではツール利用を無効化し、Claude safe-mode等で設定の混入を減らしています。ただしCLI側の企業管理設定や、CLI実装自体の動作は信頼境界の外です。

pstackの導入・更新も信頼するコードの変更です。大きな更新後は手順・権限・CLIバージョンを再確認してください。

### 4. 環境変数と資格情報

CLIログインを活用するため、多くの親環境変数を継承します。しおり専用トークンは除いていますが、無関係なDB鍵・クラウド管理鍵を同じ実行ユーザーへ与えないでください。最小権限の専用ユーザー／VMが必要です。アプリの設定ファイルにトークンを保存する機能はありません。

### 5. ログと成果物の秘密情報

SQLiteは暗号化されていません。既知の環境変数トークンと一部の鍵パターンをマスクしますが、全ての秘密を検出するDLPではありません。モデルが返す原文・添付資料・CLI stderr・認証ユーザーのホーム配下も保護対象です。exportは持ち出しに相当するため社内規程に従ってください。

### 6. ジョブの再実行とexactly-once

操作受付の重複を抑えても、外部システムの副作用が厳密に一回だけになる保証はありません。CLIが変更した直後にサーバーが落ちた場合、DB上では成否不明になります。実際の変更を照合せずに再送しないでください。

### 7. モデル出力の信頼

モデルは誤った案や不十分な成果を返す可能性があります。JSONバリデーションは形式を検査するもので、要件理解の正しさの検査ではありません。受け入れ条件、実テスト、根拠、人間の判断を別に保持します。悪意のある資料を読んだ際に、虚偽の説明を出す危険まで消せるものではありません。

## 業務導入前の最低条件

社内で許可されたモデル・CLI・認証方法と無人運用の範囲、保管場所・保存期間、担当者と承認者を確定してください。複数ユーザーで使うならSSOと案件ごとの読取り／実行／承認権限を実装し、管理操作の監査を外部保存へ拡張する必要があります。

Innerを分離した低権限環境で動かし、必要なファイルとネットワークだけを許可してください。実CLIとの結合試験、停止／再開時の照合、リポジトリ更新後の権限確認、復元訓練も必要です。

**「自作だから社内データが外に出ない」「サブスクで認証したからすべて無料」「承認画面があるから安全」とは判断できません。** データ送信先と課金経路はCLIとモデル側の設定・契約にも依存します。
