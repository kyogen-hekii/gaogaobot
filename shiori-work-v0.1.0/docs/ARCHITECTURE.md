# しおり Work — 業務用Outerの設計 v0.2

## v0.2の委任と結果確認

`delegations` に仕事の版、実行先のfingerprint、読取り／変更、最大回数、消費回数、期限、状態を保存する。利用者の「この範囲で任せて開始」で最初のInnerを予約する。回数は実行予約時に消費し、失敗・キャンセルでも戻さない。

Innerの結果は成果物に保存し、そのIDと仕事の版をOuterの結果イベントへ渡す。Outerは `review` に全受け入れ条件の `index/status/evidence` と `ready/needs_work/blocked` の判定を返す。`ready` は全条件 `met` が必要で、デモの成果物を実作業の達成根拠にできない。評価は `reviews` に成果物IDとともに保存する。

有効な委任に紐づく `propose_dispatch` は、仕事の版・実行先・作業範囲・残回数・期限をサーバーが再検証して追加実行する。結果からの続行には `needs_work` の評価を必須とする。変更された実行先や読取りから変更への拡大は停止する。委任のない提案は従来どおり個別承認を作る。

停止操作はその委任の待機ジョブと実行中ジョブ、結果確認をキャンセルする。期限は全体の一時停止中も評価する。条件編集で委任は失効し、再起動時に実行中だった委任は `interrupted` にする。以前の委任の結果を新しい委任へ流用しない。AIによる完了確定は追加せず、最後の受け入れは利用者が行う。

自然言語の作業内容が目的に合うかという意味の判断はモデルに依存する。アプリ自身はOSサンドボックスではない。セットアップが登録する編集RunnerはClaudeの `--restricted` とファイルツールのリストで範囲を限定し、シェル実行は含めない。

## 1. 設計の結論

**一つの対話・判断役と、永続的な管理アプリケーションを組み合わせる。**

チャットの外見に対して、内部の正本は会話ではなく仕事・要求・承認・成果です。AIを受付係／監督係／ルーターへ細分化せず、同じOuterが会話と結果評価を行います。Innerは専門の仕事場として接続し、細かな開発手順はInner側が担当します。

今回の実装では、Outerの自由な行動能力を広げる前に、提案から管理操作へ移る境界を検証します。**Outerは登録済み状態・投入した資料を読み、構造化された提案を返す**方式です。ブラウザ操作や社内システムを自ら探索する万能エージェントではありません。

Museは会話中心の操作体験、Grok Botは継続担当と必要時の確認、提供資料はmacro/micro/状態の責務分離の参考です。いずれかの製品の内部実装を復元したものではありません。接続部品の選択を先に固定して管理本体を設計することは避けました。

## 2. 機能の境界

| 層 | 決めること／所有するもの | 決めないこと |
|---|---|---|
| UI | 相談、対象の選択、承認、成果物確認 | CLIコマンドの組立てや認証 |
| Outer judgment | 要求整理、仕事案、依頼案、状況整理、結果の不足 | 人間になりすました承認、完了の確定 |
| Work control | 正本、承認の有効性、キュー、待機、イベント、受け入れ | 開発工程の詳細、モデルの内部推論 |
| Runner adapter | 接続先、明示的セッション、プロセス、ストリーム正規化 | 仕事の優先順位や受け入れ判断 |
| Inner workspace | 調査、設計、実装、テスト、pstack等の手順 | 無断の要求変更、自己申告のみの業務完了 |

「軽量Gateway」に管理ロジックを詰めるのではなく、**管理本体が主役、接続は交換できる一部品**にします。

## 3. 初期配置

```text
利用者のブラウザ
       │ HTTP / SSE
       ▼
しおり Work サーバー（単一ユーザー・127.0.0.1）
  ├─会話・状態・承認・成果物のUI/API
  ├─Outer Manager ── Demo / Claude CLI / Copilot CLI
  ├─Job Queue / Interval Scheduler / Event Ingress
  ├─SQLite：仕事・判断・会話・実行・セッション
  └─Runner Adapter ── Demo / Claude CLI / Copilot CLI
                             │
                      登録した開発ディレクトリ
                      規則・Skills・pstack・依存ライブラリ
```

実行ホストは手元のPCでもクラウドVMでも構いませんが、**v0.1のサーバーとCLIは同じOS環境**で動きます。CLIをリモートHTTP経由で呼ぶRunner serviceは設計上の拡張点であり未実装です。UIを開くPCにNode.jsや対象リポジトリを置く必要はありませんが、遠隔UIへの安全な接続方式は別途必要です。

実行プロセスを常駐させ続けるのではなく、一回の依頼ごとに非対話CLIを起動し、IDで会話を継続します。SDK型アダプターを追加する場合も仕事・承認・論理セッションは変更しません。

## 4. UI/UX

ホームは管理ダッシュボードではなく会話です。左のアイコンレールで相談・仕事・活動・定期確認・ライブラリ・設定へ移ります。仕事の文脈と活動は必要時にパネルで開きます。承認と条件更新は対象の版が分かるダイアログにします。

仕事の下書きは会話から生成できますが、通常の相談をすべて仕事に変換しません。会話には仕事・承認・成果物へのカードを置き、その場から開けるようにします。複数案件を一つの会話の履歴だけで管理せず、仕事を開けば専用会話へ移ります。

入力中の下書きを画面遷移で保持します。本文と成果物はテキストとしてエスケープ表示し、モデルのHTMLをそのまま実行しません。検索は現時点でクライアント内の文字列検索です。埋め込み検索・RAGは導入していません。

画面のモデル表示でDemoと実Providerを区別します。静的preview.htmlは、さらに「画面体験用」のバナーを出し、実行基盤と誤認させません。

## 5. Outerの判断契約

入力は、管理方針、今回の依頼、会話の直近16メッセージ、対象の仕事の正本、直近の判断、関連資料、実行先カタログです。資料ごとの量を制限し、無制限に全履歴を詰め込みません。

応答は次の形式です。

```json
{
  "reply": "利用者向けの整理と次の判断",
  "actions": [
    {
      "type": "propose_work",
      "title": "設計レビューの準備",
      "objective": "レビューで未決事項を判断できる状態にする",
      "acceptance": ["未決事項と根拠が対応している"],
      "constraints": ["コードを改修しない"]
    }
  ]
}
```

許可する操作は4種類です。

| 操作 | 効果 |
|---|---|
| propose_work | 下書きの仕事と専用会話を作る |
| propose_dispatch | 有効な委任内ならサーバー検証後に実行予約。それ以外は個別承認 |
| save_note | 会話由来の資料・メモを保存する。要求の正本を無断更新しない |
| propose_routine | 無効状態の定期確認案を作る。有効化は人間 |

`approve`、`complete_work`、任意シェルコマンドなどは契約にありません。モデル出力を検査し、不正な操作が含まれるバッチはDBトランザクションを戻します。JSONを返しただけで業務的な正しさが保証されるわけではありません。

Claude／CopilotをOuterに使う場合も、専用の作業場所とツール無効設定で起動します。InnerのSkills一式をOuterへコピーしません。現在は汎用的なツール探索ではなく、登録済みRunnerへの依頼提案という狭い入口です。

## 6. 状態モデル

| エンティティ | 主な情報 |
|---|---|
| conversations / messages | 会話ID、仕事との対応、原文、出力カード |
| works | 目的、条件、制約、版、状態、関連資料ID |
| approvals | 実行先、依頼文、要求版、設定fingerprint、有効期限、digest |
| delegations | 要求版・実行先・mode・最大/消費回数・期限・停止理由 |
| reviews | 条件ごとの評価・根拠・判定・対象成果物ID・要求版 |
| decisions | 人間による条件更新、実行承認、受け入れ判断 |
| artifacts | 元資料、メモ、実行結果、出典種別、仕事・実行への参照 |
| jobs | role、状態、実行先、セッション、進捗、終了結果、PID |
| sessions | 論理ID、所有対象、vendor ID、設定fingerprint、世代 |
| routines | 対象、間隔、確認指示、有効状態、次回日時 |
| locks | 実行中／要照合の仕事場の排他 |
| events / dedup | 状態変化と操作ID、重複排除 |

SQLiteは最小の汎用entities表とevents表で実装しています。大規模検索・複数ユーザー・正式スキーママイグレーションは次の段階です。eventsはアプリ上で追記ですが、改ざん耐性を持つ外部監査ストアではありません。

仕事の主な遷移は次の通りです。

```text
draft → waiting_approval → queued → running → review → done
                              │        │
                              └─失敗─→ blocked
blocked / review → 新しい依頼 → waiting_approval
```

実行状態は、`queued / running / cancel_requested / succeeded / failed / canceled / interrupted`です。仕事と実行は別なので、runがsucceededでもworkはreviewに留まります。要求更新はrevisionを進め、未処理の承認を無効化します。

## 7. 一往復

1. 入力原文を永続化し、Outerジョブを受け付ける。
2. 最新状態からコンテキストを組み立て、Outerが整理・提案する。
3. 仕事と条件を確認し、Innerへの依頼案を作る。
4. 人間が依頼・実行先・変更可否・要求版を確認して承認する。
5. キューが同一セッションと仕事場の排他、上限、承認の有効性を確認する。
6. 明示的セッションIDを指定してInnerを動かす。
7. 成果物を保存し、仕事を受け入れ待ちにする。
8. Outerを起動して条件との不足を整理する。デモは定型応答、実Provider時は実推論。
9. 不足があれば同じ仕事に追加依頼。満たせば人間が条件ごとに受け入れる。

成果物の要約や再評価に失敗しても、Innerの成果は先に保存しています。自己評価だけで自動完了させません。

## 8. 外ループ

常駐サービスがイベントと時計を受け付け、必要なときだけOuterを起動します。LLMを空回しする無限ループはありません。

現版の定期確認は「作成時点からN分間隔」です。Cron式、営業日カレンダー、タイムゾーン別定刻ではありません。サーバー停止中は動かず、再開時の過去の未実行分を一回へまとめます。対象仕事が完了すると、その仕事の定期確認を停止します。

外部イベントは、Bearerトークン付きの汎用APIで受付可能です。同じイベントID・同じ内容は同一処理へ戻します。同じIDで別内容なら競合として拒否します。特定サービスの署名検証やSlack／Teams連携は未実装です。

自律管理の範囲は、状態の整理・依頼提案・定期確認案までです。現在の版は仕事ごとのInner開始を毎回承認するため、「完全放置で改修を進めるBot」ではありません。将来、自動実行を許す場合は、期限・操作・対象・予算を持つ明示的な委任契約を追加します。

## 9. 接続方式の選択

| 方式 | 利点 | 課題 | 現版 |
|---|---|---|---|
| CLIをターンごとに起動して明示IDで継続 | 二製品を共通化しやすい。既存CLI設定を使う | 出力形式・版差、細かい権限相談は弱い | 採用 |
| Agent SDK／構造化クライアント | メッセージ・中断・permission callbackを扱いやすい | SDK固有差、認証／契約を別途確認 | 交換先候補 |
| 常駐対話CLI＋PTY | 人間と同じ端末に接続しやすい | 画面解析、入力待ち、キー操作が壊れやすい | 不採用 |
| チケット割当だけで一方通行 | 非同期バッチに向く | 同じ仕事への相談・追加指示が遠くなる | 単独方式にはしない |

初期採用理由は、CLIが最終的に最良だからではなく、**管理の状態モデルを先に動かしながら二つのハーネスに対応できるため**です。SDKへ替えてもUI／仕事ID／承認／イベントを捨てないようにします。

## 10. 今後の境界

業務で一人の試用を越える前に必要なのは、SSO・所属と案件ごとの認可、承認者の認証、データ保管方針、監査ログ、認証情報隔離、OSとネットワークの制限、秘密情報の出力検査、プロセスの恒久管理です。

次に能力を広げるなら、Outerに無制限なシェルを与えるのではなく、承認済み情報源の読取りを狭いツールとして追加します。そのうえで、未達の再計画や自動進行の範囲を評価します。多段の管理AIやSwarmは前提にしません。
